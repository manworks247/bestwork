# ML Challenge 2026: Business Entity Resolution Solution Template

---

## 1. Executive Summary

We resolve business entities with a country-partitioned pipeline: a multi-key
inverted-index blocker generates at most 12 high-precision candidates per
Source-1 entity, and a LightGBM classifier over 18 RapidFuzz/token-overlap
features accepts pairs above a probability threshold tuned directly for the
competition metric (macro F₀.₅, singletons included). The design is fully
streaming, so the same code runs unchanged on a 4 GB laptop, Google Colab, or
Amazon SageMaker, and it uses only the provided records — no external data,
embeddings services, or lookups.

---

## 2. Methodology

### 2.1 Problem Analysis

EDA on the training data showed:

* **Name noise** — legal-suffix variants (Pvt/Private, Ltd/Limited, Corp/
  Corporation, SARL/SASU for France), "&" vs "and", punctuation, word-order
  transpositions, typos, spacing differences ("Bio Tech" vs "Biotech").
* **Address noise** — component reordering (Indian addresses frequently store
  city/state in shuffled order), abbreviations (Rd/Road, St/Street),
  missing PIN/ZIP codes, landmark references ("Near Fortis Hospital"),
  unit/floor prefixes.
* **Country is a reliable hard key** — matches never cross countries, and the
  test set introduces France, so the pipeline treats country as an *open set*
  of string labels (any unseen label simply becomes its own partition; nothing
  is hard-coded to US/India).
* **Cardinality** — a Source-1 entity matches 0–8 records; singletons are a
  significant fraction, and F₀.₅ rewards predicting an empty list correctly,
  so the acceptance threshold matters as much as the model.

### 2.2 Solution Strategy

**Approach Type:** Blocking + pairwise gradient-boosted classifier (hybrid
lexical blocking, learned matcher).

**Core Innovation:** frequency-aware multi-key blocking whose *exact* top-K
output is both the model input and `candidate_pairs.tsv` (no hidden filtering
stages), plus threshold selection that directly optimises the macro-F₀.₅
objective on a held-out entity split — including singleton credit.

---

## 3. Candidate Generation (Blocking)

Per country partition, every Source-2/3 record is indexed under:

| Key | Weight | Purpose |
|---|---|---|
| full compressed core name (suffixes stripped, alnum only) | 4.0 | exact-name variants |
| 8-char compressed-name prefix | 3.0 | typos/truncations at the tail |
| first two core name tokens | 3.0 | word-order stable brand key |
| each core name token (≤6, len ≥3) | 1.0 | recall net for reordered names |
| first core token + first house number | 2.0 | name+address anchor |

Posting lists are capped at 400 ids (over-frequent keys are ignored at query
time), and query-time weights are scaled by `1 + 2/(1+0.05·df)` so rare keys
dominate. Each Source-1 record keeps its **top-12** candidates by accumulated
weight — this exact list is written to `candidate_pairs.tsv` and is what the
model scores (avg ≈ 6–9 candidates per entity after weak-key filtering, a
reduction of >5 orders of magnitude versus the full cross product).

**How true matches are preserved:** keys are redundant (name-only, prefix,
token, name+number), so a pair survives if *any* of the five views agrees;
blocking recall measured on a held-out training split is the recall ceiling
reported in §5.

## 4. Matching Model

**Features used (18):**

* Name: RapidFuzz ratio / token_sort / token_set / partial ratio, token
  Jaccard, compressed-name ratio, common-prefix fraction, length difference.
* Address: ratio, token_set, token_sort, token Jaccard, digit-set Jaccard,
  first-house-number equality, address-missing flag.
* Context: blocking score, blocking rank, source flag (S2 vs S3).

**Model type:** LightGBM binary classifier (600 rounds, early stopping,
`num_leaves=63`), trained on candidates generated by the *same* blocker over
the training sources, labelled with `train_ground_truth.tsv`. LightGBM is MIT
licensed and has ~10⁵ parameters — far under the 8B cap.

**Threshold selection method:** a 20% held-out split *by Source-1 entity*;
sweep t ∈ [0.20, 0.96] and keep the argmax of macro F₀.₅ computed exactly as
the organisers do (per-entity, singletons scored 1.0/0.0).

---

## 5. Results & Error Analysis

* **F_0.5 Score (macro):** see `models/matcher_lgbm.txt.meta.json`
  (`val_macro_f05`) produced by the training run — reproduced by
  `python -m src.pipeline`.
* **Common false positives:** franchise/chain branches sharing a name with
  different addresses in the same city; sibling companies sharing a rare
  brand token.
* **Common false negatives:** heavy address-only records whose names were
  legally renamed (DBA), and transliteration variants where every name token
  differs.

---

## 6. Conclusion

A carefully weighted lexical blocker plus a small gradient-boosted matcher,
tuned directly on the competition metric, delivers strong precision-first
performance while remaining reproducible on commodity hardware in every
environment (local / Colab / SageMaker) with zero external data.
